FAILURES (verbatim where available)
1. T10 strict failures, all 6 runs, across all reps: the agents renamed the node id on a file rename, because my task text said "ids are file stems". Expected: only paths change. Agent report: "Renamed `request-validate` to `request-validate-log`". This is an ambiguity in my task wording, not a representation effect; I report the lenient column. The R4 run also edited the renamed node's summary text (a collateral change), so it fails even leniently. The R1 re-run also edited the summary.
2. R2 CLI whole-model validation breaks drift work (T10, T12): after the code changed, the model is already invalid (stale paths), so every write was rejected. Evidence: T10 R2 had 37 rejected CLI calls, T12 R2 had 9 then 15. The agents bypassed it by faking files. Quote (T10 R2): "I briefly created empty stub files at code/src/orders/fulfillment/picker.py and code/src/gateway/apischema/request_validate.py. I deleted both once the edits went through". Quote (T12 R2 rep): "`python smap.py check` passes ... only because I left a stub file in code/." That second run ended partial: it left rules-engine and rules-eval in place, put chargeback-intake as a component leaf, and left the old SchemaViolationError raise on matcher (strict fail, score 0.7).
3. CLI missing verbs, found by agents: T11 R2 said "The CLI has no verb to remove a raise. I mistakenly ran `raise checkout-validate PaymentDeclinedError --remove`, which added a junk raise entry. To clear both raises, I deleted the node with `rm --prune-edges` and re-created it". T12 R2 did the same for matcher. Delete-and-recreate lost nothing here only because the agent re-added the edges by hand; it would lose `reviewed` stamps and history.
4. Parent/child deadlock in the validator: "leaf must own paths" plus "non-leaf must not own paths" meant a parent could not be emptied or created before its child. Agent quote (T12 R2 rep): "A parent with no paths is rejected as a leaf, and a parent with paths is rejected once it has a child, so the CLI can't create that pair." T12 R2b's agent got around it by renaming and re-parenting old nodes ("I moved rules-engine under payments, renamed it `chargebacks`"). The end state was correct, but it was not an intended path. `rm` needs a recursive/cascade option.
5. R2b (incremental validation) removed the stale-path blockade (T10 R2b: 1 rejection vs 37) but did not fix #4 (T12 R2b still 12 rejections).
6. No agent ever invented a node or edge on the read/update tasks. The only extras were the rename ids above and the one partial T12 R2 run.
7. Agent self-reports of "did not run a validator" appeared in most R1/R3/R4 update runs. The final-state validator found 0 problems in every run I scored (so the unchecked updates happened to be right).

ANSWERS
- Most reliable + cheapest for READ: R2 (CLI) on cost (fewest calls, lowest tokens in 3 of 4 tasks). Correctness is tied at 100% for everything on 4 read tasks, so reliability cannot be ranked.
- UPDATE: R2 was cheapest by a wide margin (3 calls for rename/move vs 16-17 for R1/R3), and 100% on all five update tasks including the cycle trap. R4 was the best file-based form (6 calls rename, 4 move). R3 rename/move needed a manual FQN rewrite; both passed, but it is the most mistake-prone surface (replace-all of dotted names) and one agent said "I did not re-read the file or check the result after the edits", yet was correct.
- DRIFT: R1/R3/R4 reliable on T11/T12 (all passed); R2 as built was worst because of whole-model validation. R2b is better but still deadlocked on parent removal. Cost per drift run was 50-90k tokens everywhere; R4 used 91k on T12 (9 calls but big reads).
- Are CLI-gated writes better than direct edits? On this sample, no measurable reliability gain, because direct editors also scored 100% and invented nothing. The cycle trap (T9) passed in all four, including R1/R3/R4 where agents traced the cycle by hand (they said so: "I checked the cycle from the dependency edges in system.json only"), so the validator was not needed to prevent it here. The gate's real benefit was cost (fewer calls) and not-leaving-garbage; its real cost was the drift blockade and missing verbs. A gate only helps if it never blocks legitimate repair work.
- What the validator must catch: duplicate/missing ids; unknown parent; kind/depth mismatch; dangling dep targets and stale FQNs (R3); self-deps; cycles (with the cycle path printed); leaf-only deps; dep kind and handling enums; exception registry; path-glob matches zero files; one-owner-per-file; summary length. It must also: (a) treat pre-existing problems as non-blocking (compare to baseline); (b) allow removing or re-parenting whole subtrees atomically (`rm --recursive`, no leaf-with-no-path deadlock); (c) provide verbs for every operation: raise rm, dep rm, rename, move, delete subtree; (d) never encourage faking stub files (make "ownership check vs. filesystem" a warning in drift mode).
- Recommended caps (judgment, not proven by this data): node summary <=200 chars; <=10 children per node (this system used <=5); depth <=4 below the system. Files: R1 split per subsystem (about 40 KB total, 220-260 lines each) was cheap to navigate; the single 2,933-line JSON forced offset reads and was the most expensive read (T1 78k). I would cap any single model file around 1,000 lines or 25 KB.
- Honest caveats: sample is tiny (1 run per cell; n=2 on T10/T12 only); sonnet only; agents were fresh, short-lived sessions with the full format spec in the prompt, not long-running sessions with drifting context; the task set was mostly at ceiling, so there is little discriminating power; the T10 ambiguity and the CLI design flaws (#2-#4) shaped the drift results more than the representations did; the 124-node scale is small and a larger model would likely hurt R3/R4 reads more; the "no scripts/no direct reads" rules were not enforced. Several opus and repeat runs (T10 n2/n3, T12 n2/n3, T11 R2b, opus x8) died on rate limits and are excluded; I stayed under the cap of ~24 additional fresh runs after the reset (8 launched, all completed).
